1980s–1990s

Rule-Based Expert Systems

Early security tools relied on predefined rules and signatures. These systems recognized known patterns but struggled with new or changing threats.

Foundation: rule-based reasoning
2000s

Statistical Detection and Log Analysis

Security teams centralized logs and used statistical methods to identify unusual events across networks, endpoints, and applications.

Growth: SIEM and anomaly detection
2010s

Machine Learning for Behavioral Analytics

Machine-learning models began supporting malware classification, user behavior analytics, fraud detection, and alert prioritization.

Expansion: predictive analytics
2020–2022

Automation and AI-Assisted SOC Workflows

Security platforms combined analytics with automation to enrich alerts, correlate evidence, recommend actions, and reduce repetitive analyst work.

Operations: orchestration and triage
2023–Present

Generative AI and Security Copilots

Generative AI can summarize incidents, explain queries, draft investigation steps, and help analysts navigate security data. Human validation remains necessary because results may be incomplete or inaccurate.

Current focus: human-AI collaboration

Artifact 2: Evaluating an AI-Generated Phishing Analysis

A fictional and sanitized cybersecurity exercise demonstrating how AI can assist a SOC analyst without replacing human verification.

Purpose

Connect AI learning with real-world SOC decision-making

This artifact evaluates whether an AI-generated security analysis correctly identifies a phishing attempt, explains the evidence, recommends an appropriate severity, and proposes safe response actions. No real organizational data, employee information, internal logs, or confidential incidents are used.

Step 1

Fictional Incident Scenario

A user receives an urgent email claiming that their Microsoft 365 password will expire within 30 minutes. The message asks the user to sign in through a shortened URL. The display name is “Microsoft Security,” but the sender domain is unrelated to Microsoft.

Step 2

Prompt Submitted to the AI Tool

Act as a SOC analyst. Analyze this fictional security incident.

Identify:
1. The likely incident classification
2. Indicators of compromise
3. Recommended severity
4. Immediate containment actions
5. Investigation steps
6. User guidance
7. Limitations or assumptions

Step 3

AI Analysis Summary

  • Classified the message as a likely credential-phishing attempt.
  • Identified urgency, sender-domain mismatch, and shortened URL.
  • Recommended isolating the message and blocking the URL.
  • Suggested checking sign-in activity and contacting the user.
  • Noted that severity depends on whether the link was clicked.
  • My analyst judgment: I would explicitly ask whether the URL was clicked because urgency alone does not confirm user action or compromise.

Step 4

Human Analyst Evaluation

What the AI did well

It recognized common phishing indicators and proposed reasonable first-response actions.

What required improvement

A final severity should not be assigned until the analyst knows whether the user clicked the link, entered credentials, or generated suspicious authentication activity.

Required analyst validation

Review message headers, URL reputation, email gateway data, endpoint activity, sign-in logs, and whether other users received the same message.

Introduction & Description

A sanitized phishing scenario used to evaluate whether an AI assistant can produce a useful initial SOC analysis.

Objective

Assess AI-generated classification, evidence, severity guidance, investigation steps, and limitations against analyst judgment.

Process

Create a fictional scenario, prompt the AI, review its output, identify missing evidence, and define required human validation.

Tools & Technologies

Generative AI prompting, phishing-analysis concepts, email headers, URL reputation, identity logs, endpoint telemetry, and SOC triage practices.

Value & Unique Value

The artifact shows that I do not treat AI output as a final decision; I connect recommendations to evidence and user actions.

Relevance

Relevant to SOC teams adopting AI assistants while preserving investigation quality, privacy, and analyst accountability.

Supporting Sources

Artifact 3: Machine Learning Model Evaluation for Phishing Detection

A portfolio-ready classification exercise demonstrating data preparation, model evaluation, cybersecurity interpretation, and responsible use of machine learning.

Purpose

Demonstrate a new technical skill through model evaluation

Artifact 1 demonstrated research and technical communication, and Artifact 2 demonstrated AI-output evaluation. Artifact 3 adds a different competency: interpreting the performance of a supervised machine-learning classifier designed to identify potentially malicious email messages.

Problem Statement

Can a classifier support phishing-email triage?

Security teams may receive a high volume of suspicious messages. A machine-learning model can help prioritize likely phishing messages, but it should support—not replace—analyst review.

Target Audience

Who This Artifact Is For

  • AI/ML educators reviewing applied model-evaluation skills.
  • SOC leaders interested in phishing-triage use cases.
  • Hiring managers assessing technical and analytical ability.
  • Students learning responsible cybersecurity classification.

Project Workflow

From Raw Email Features to an Evaluated Classification Model

1Define the problem

Classify fictional email records as legitimate or phishing.

2Prepare the data

Clean fields, encode labels, and separate training and test data.

3Engineer features

Convert raw message signals into model inputs—for example, map urgency terms to a binary indicator, compare sender and display-name domains, identify shortened URLs, and encode attachment or credential-request flags.

4Train a classifier

Fit a simple supervised-learning model using sanitized data.

5Evaluate performance

Review precision, recall, F1 score, and the confusion matrix.

6Interpret responsibly

Explain limitations and identify where analyst validation is required.

Signals Used by the Model

Evaluation Measures

Why Accuracy Alone Is Not Enough

Precision

Of messages flagged as phishing, how many were actually phishing?

Recall

Of all phishing messages, how many did the model detect?

F1 Score

How well did the model balance precision and recall?

Challenge

False Positives

Legitimate messages may contain urgent language or unfamiliar links. Excessive false positives can create alert fatigue and reduce trust in the model.

Risk

False Negatives

A missed phishing message may reach a user. In a security context, recall is especially important because false negatives can carry operational risk.

Response

Human-in-the-Loop Review

Model output should be combined with mail headers, URL reputation, authentication logs, endpoint activity, and analyst judgment.

Simplified Code Example

Illustrative Python Evaluation Workflow

from sklearn.metrics import (
    accuracy_score,
    precision_score,
    recall_score,
    f1_score,
    confusion_matrix
)

predictions = model.predict(X_test)

print("Accuracy:", accuracy_score(y_test, predictions))
print("Precision:", precision_score(y_test, predictions))
print("Recall:", recall_score(y_test, predictions))
print("F1:", f1_score(y_test, predictions))
print(confusion_matrix(y_test, predictions))

This code illustrates the evaluation stage. A complete project would also document data preparation, feature engineering, train-test separation, model selection, and reproducibility.

Operational Impact

Translate Metrics into SOC Workload

With illustrative precision of 92.9%, roughly 7 of every 100 messages flagged as phishing would be false alarms. A SOC must plan for those reviews rather than treating the score as an abstract model metric. For a five-person team, the practical question is whether the triage workflow can absorb those false positives while still investigating high-risk alerts quickly.

Feature engineering also affects this workload. “Urgency” is not a raw number by itself; it must be extracted from message text using a defined rule or text-processing method. The same applies to sender mismatch, URL characteristics, attachment types, and credential requests.

Reflection

What I Learned from Artifact 3

This artifact helped me understand that model performance must be evaluated in relation to the business and security problem. A high accuracy score can hide important errors, especially when one class is more common than another. For phishing detection, false negatives and false positives affect security operations in different ways.

I also learned that machine-learning results should be communicated in language the target audience can understand. A SOC leader needs to know how the model changes analyst workload and security risk, while an AI/ML reviewer needs to understand the evaluation method. This artifact demonstrates my ability to connect technical measures with practical cybersecurity decisions.

Artifact 4: Responsible AI Security Risk Assessment

A governance-focused artifact evaluating the risks, controls, and human oversight needed before using an AI assistant in a Security Operations Center.

Purpose

Demonstrate AI governance, risk analysis, and policy thinking

The previous artifacts demonstrated incident analysis, research, communication, and model evaluation. This fourth artifact adds a new competency: assessing whether an AI-enabled security tool can be used safely, transparently, and responsibly in an operational environment.

Fictional Use Case

AI Assistant for SOC Alert Triage

A fictional organization is considering an AI assistant that summarizes SIEM alerts, recommends investigation steps, and drafts incident notes. The assistant does not take autonomous containment actions. Analysts remain responsible for all final decisions.

Target Audience

Who This Artifact Is For

  • Cybersecurity leaders evaluating AI-enabled tools.
  • Risk, privacy, legal, and compliance stakeholders.
  • SOC analysts who will review AI recommendations.
  • AI/ML educators assessing responsible-use competencies.

Assessment Method

Five-Step Responsible AI Review

1Define the use case

Clarify what the AI may and may not do.

2Identify risks

Review accuracy, privacy, bias, security, and operational impact.

3Design controls

Add access restrictions, validation, logging, and approval steps.

4Test performance

Evaluate outputs using representative, sanitized scenarios.

5Monitor continuously

Track errors, drift, incidents, and analyst feedback.

Risk Register

Key Risks and Recommended Controls

This register uses a fictional SOC assistant and does not contain employer, university, or production-system information.

RiskPotential ImpactLevelRecommended Control
Incorrect alert summaryAnalyst may investigate the wrong issue or overlook evidence.HighRequire analyst validation against source logs before action.
Sensitive data exposurePrompts or outputs may contain confidential user or system information.HighUse data minimization, masking, approved retention, and access controls.
Automation biasAnalysts may trust confident AI wording without sufficient review.MediumDisplay uncertainty, require evidence citations, and train analysts.
Uneven performanceThe tool may work better for common alerts than unusual attacks.MediumTest across diverse scenarios and monitor performance by alert type.
Prompt injection or malicious inputAdversarial content may influence the assistant's recommendations.HighSanitize inputs, isolate untrusted content, apply guardrails, and log activity.
Weak accountabilityIt may be unclear who approved an action or changed a conclusion.MediumMaintain audit logs and assign a named human decision owner.

Control Area 1

Human Oversight

AI recommendations must remain advisory. Analysts verify evidence, set severity, approve containment, and document the final decision.

Control Area 2

Privacy and Data Handling

Only necessary, authorized, and sanitized data should be processed. Retention and sharing must follow organizational policy.

Control Area 3

Security and Access

Use least privilege, strong authentication, input controls, change management, logging, and periodic access review.

Control Area 4

Transparency

The assistant should distinguish facts from assumptions, show supporting evidence, and communicate uncertainty clearly.

Control Area 5

Testing and Monitoring

Track accuracy, false guidance, latency, analyst overrides, user feedback, drift, and security incidents.

Control Area 6

Incident and Exit Planning

Define how to disable the tool, investigate harmful outputs, notify stakeholders, and return to manual workflows.

Recommendation

Conditional Pilot Approval

The fictional AI assistant should be approved only for a limited pilot using sanitized, nonproduction scenarios. It should not be allowed to block accounts, isolate devices, or close incidents automatically.

  • Human review is mandatory for every recommendation.
  • All prompts, outputs, overrides, and decisions are logged.
  • Privacy and security teams approve data handling.
  • Success criteria and stop conditions are defined before launch.
